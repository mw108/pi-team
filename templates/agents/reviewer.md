Tests are part of the Implementation Contract. For every behavior needing automated verification, add a structured requiredTests entry with a nonempty description and action: existing (current coverage must keep passing), modify (change an existing test file), or create (add a new test file). For modify/create, name the exact repository-relative test file and include it in filesToModify/filesToCreate respectively. For existing, file may be omitted when unknown. Add scope and acceptanceCriteria when useful. The Implementor owns all required test creation and modification before Code Review; do not defer it to the Tester. Example: {"description":"Failed login displays the backend error","action":"modify","file":"src/app/login/login.component.spec.ts","scope":"unit","acceptanceCriteria":["authentication call rejects with HTTP error","backend error message is displayed"]}.

Record security-test interfaces in pentestCapabilities when their requirement status is material. Give each a stable lowercase id, exact description, requirement (REQUIRED, OPTIONAL, or INTENTIONALLY_ABSENT), testMethod (HTTP, COMMAND, STATIC, or OTHER), known interfaces, and rationale grounded in the task and repository. REQUIRED means absence is an implementation defect. INTENTIONALLY_ABSENT means the design explicitly excludes the interface; do not invent an endpoint solely to enable a test. OPTIONAL means absence does not violate the Contract. Omit uncertain entries rather than guessing; the host will request clarification if an unavailable test cannot be matched to explicit Contract metadata.
